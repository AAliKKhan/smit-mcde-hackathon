# Implementation Plan: Indus Weave HR Data Warehouse Pipeline

**Branch**: `001-hr-pipeline` | **Date**: 2026-10-25 | **Spec**: [specs/001-hr-pipeline/spec.md](spec.md)
**Input**: Feature specification from `/specs/001-hr-pipeline/spec.md`

## Summary

Build a Python 3 + SQL batch pipeline that lands 12 messy HCM exports (1,316 employees,
345,280 punches, 6 months) into a `raw` schema as immutable TEXT, cleans them into typed
`staging` tables (dedupe, device mapping, clock-drift correction, 2-minute punch collapse, leave
flattening), derives `attendance_daily` from 21 business rules, models a star warehouse with an
SCD2 employee dimension, answers 10 CFO questions in SQL, and proves everything with automated
DQ checks written to `dq_results` — delivered as a one-command rebuildable GitHub repo with a
5-minute CFO story about rising overtime cost.

## Technical Context

**Language/Version**: Python 3.13 (team runtime; target-compatible with 3.10+)
**Primary Dependencies**: pandas, SQLAlchemy (sqlite3 driver), plus stdlib (`hashlib`,
`json`, `pathlib`); `pytest` for self-checks; `requirements.txt` pins all
**Storage**: SQLite single file `db/indus_weave.db` — schemas `raw`, `staging`, `warehouse`,
`dq_results` (table). Allowed by case study when a team can't run PostgreSQL.
**Testing**: `pytest` + SQL invariant probes; DQ layer (`quality/`) doubles as the graded
verification suite
**Target Platform**: Windows/macOS/Linux developer machines (mentor rebuild on clean machine)
**Project Type**: single project — CLI/batch pipeline, no web/mobile surface
**Performance Goals**: full rebuild from raw ≤ 10 minutes on a laptop (345k punches × 6 months)
**Constraints**: Python + SQL only for Stages 1–6; no Spark/Cloud/BI; raw files immutable;
rubric timebox 8 hours with effort weighted answers 25 > cleaning 20 > model 15 = DQ 15 =
CFO 15 > code 10
**Scale/Scope**: 12 source files (~25 MB, ~414k source rows), 10 analytic queries, 6-month
window Apr–Sep 2026 (dim_date through Oct 31 for spillover check-outs)

**Structure Decision**: Single-project layout at repository root, mirroring the case study's
required deliverable tree exactly (`ingestion/ transform/ warehouse/ analytics/ quality/
presentation/`) with `tests/` and `docs/` added for the quality gates. Data stays in `data/`
untouched; generated artifacts (DB, CSVs) are reproducible from code, DB gitignored, result CSVs
committed as evidence.

## Pipeline execution order (maps to tasks.md)

```text
run_pipeline.py
  1. warehouse/ddl/00_schemas.sql + 10_staging.sql + 20_warehouse.sql + 30_indexes.sql
  2. ingestion/load_raw.py        → Gate R (counts.py verifies)
  3. transform/01…06              → staging tables (+ rejected_punches, logs)
  4. transform/07_attendance_daily.py → staging.attendance_daily
  5. warehouse/build_warehouse.py → dims (SCD2, date spine) then facts
  6. analytics/run_all.py         → 10 CSVs                     → Gate Q
  7. quality/run_dq.py            → dq_results                  → Gate D
  8. presentation/cfo_findings.md evidence re-execution (manual verify before Gate P)
```

Each stage is independently runnable (idempotent create-or-replace) so teammates can work
US-by-US in parallel after the DDL lands.
